- **읽기 상태:** 완전히 읽지 못한 글은 없다. 다만 다음 글은 정밀도가 낮다.

  - 2, 40번: 끝부분을 확인하지 못했다.
  - 공통: 이미지 안에 든 로그, 그래프, 코드는 확인하지 못했다.

## 3. 유형별 템플릿

각 템플릿은 **뼈대**(섹션 순서)와 **필수 체크리스트**로 구성된다. 체크리스트 항목 뒤 괄호 안 숫자는 근거가 된 샘플 번호다.

### T 트러블슈팅

**뼈대**
1. **증상:** 로그 한 줄, 알림 문구, 수치 대조, 모순된 관측 중 하나로 시작한다. 맥락은 3문단 안에 끝낸다.
2. **환경과 범위:** 버전 표와 일반화 고지("사내 코드라 이름은 바꿨다")를 둔다.
3. **조사 경로:** 가설 → 검증 → 기각을 반복하거나, 위 계층에서 아래 계층으로 내려간다.
4. **근본 원인과 기전:** 다이어그램이나 타임라인으로 "왜 그렇게 되는가"를 보인다.
5. **수정:** 임시 조치와 근본 조치를 나누고, 버린 대안과 그 이유를 적는다.
6. **검증:** 문제를 일으킨 것과 같은 조작으로 다시 시험하고, 전후 수치를 비교한다.
7. **재발 방지:** 알림, IaC, 테스트, 남은 과제를 적고, 교훈을 원칙 문장 1~3개로 줄인다.

**변형:** 결론을 앞에 두고 본문을 그 증명으로 쓰는 방식(19, 23, 119). 가설을 헤딩으로 세우는 추리형(110, 112, 113). 계층을 따라 내려가는 방식(106, 107, 122).

**필수 체크리스트**
- [ ] 도입 3문단 안에 구체적인 증상이 있다. 일반론 서론으로 시작하지 않는다. (23, 106 / 반례 122, 123)
- [ ] 틀렸던 가설과 그것을 기각한 근거가 남아 있다. (23, 107, 112)
- [ ] 원인을 문서 인용만이 아니라 재현이나 단일 변수 실험으로 증명했다. (107, 110 / 반례 122)
- [ ] 수정을 같은 조작으로 재검증했다. 남은 나쁜 수치도 숨기지 않는다. (107, 114, 118)
- [ ] 관련 업스트림 이슈나 PR 번호, 수정이 포함된 버전을 적었다. (23, 106, 108)
- [ ] 분량을 깊이에 비례해 배분했다. 사소한 단계는 짧게 줄이고 핵심 원인에 집중한다. (106)

### H 실습·검증

**뼈대**
1. **계기와 질문:** 계기를 밝히고 "~인가?" 형태의 검증 질문으로 좁힌다. 가능하면 예상(가설)도 적는다.
2. **결과 미리 보기 (선택)**
3. **최소한의 개념:** 실험을 이해하는 데 필요한 것만 설명한다.
4. **환경과 설계:** 버전 표, 변인, 대조군, 측정 절차를 적는다.
5. **실험 블록 반복:** 조건 → 코드 → 원시 출력 → 표 → 해석을 한 단위로 반복한다.
6. **원인 분석:** 프로파일러, 트레이스, 설정 덤프로 "왜"를 설명한다.
7. **한계와 하지 않은 것**
8. **정리:** 요약표나 권장 사항, 다른 환경에 가져갈 판단 규칙, 저장소 링크로 끝낸다.

**필수 체크리스트**
- [ ] 바꾼 변수 하나 외에는 똑같은 대조군이나 기준선이 있다. (8, 21, 100, 111)
- [ ] 반복 횟수, 워밍업, 대표값과 분산을 적었다. (1, 21, 47 / 반례 102, 111)
- [ ] 측정하기 전에 측정하려는 현상이 실제로 일어났는지 먼저 보였다. (7, 21, 47)
- [ ] 예상과 다른 결과와 자기 측정 오류를 숨기지 않았다. (3, 21, 22, 100)
- [ ] "재지 않은 것"을 밝혀 일반화 범위를 제한했다. (21, 104, 111)
- [ ] 측정값과 인용값을 구분했다. (반례 102)
- [ ] 섹션 제목을 발견 내용의 문장으로 써서, 목차만 읽어도 결론을 알 수 있다. (21, 116)

### C 개념 해설

**뼈대**
1. **독자의 의문:** 독자가 겪은 증상, 에러, 의문으로 시작하고 답할 질문이나 범위를 예고한다.
2. **정의와 최소 재현:** 한 문장 정의 뒤에 가장 작은 실행 예제를 둔다.
3. **존재 이유:** 이전 방식의 한계로 새 방식이 필요한 이유를 설명한다(진화 서사).
4. **메커니즘:** 한 축(시간, 호출, 진화 순서 중 하나)을 정해 끝까지 지킨다.
5. **함정과 오해 교정**
6. **실무 판단 기준:** "써야 하는가", 반대 조건, 비교를 다룬다.
7. **마무리:** 요약, 독자가 가져갈 진단 질문이나 규칙, 참고 자료로 끝낸다.

**필수 체크리스트**
- [ ] 흔한 오해를 하나 이상 명시적으로 바로잡았다. (24, 38, 39, 45)
- [ ] 글 전체를 관통하는 예제 하나를 반복해서 썼다. (80, 81, 94)
- [ ] 비유나 단순화를 쓴 뒤 그것이 깨지는 지점을 밝혔다. (40, 41, 45, 80)
- [ ] 분야 관습에 맞는 1차 근거를 달았다(§4 참조). (2, 24, 35, 38, 120)
- [ ] 모르거나 확실하지 않은 부분을 그 자리에서 표시했다. (71, 72, 81)
- [ ] 알려진 반론이나 트레이드오프를 다뤘다. (85 / 반례 86)

### G 가이드

**뼈대**
1. **문제와 동기**
2. **범위와 기준 환경:** 대상 독자, 목표, 도구 버전과 OS, 작성일을 적는다.
3. **개념 한 컷:** 표나 다이어그램 하나로 전체 그림을 보인다.
4. **가장 짧은 성공 경로:** 스모크 테스트와 성공 판정 기준을 먼저 제시한다.
5. **기능별 단계:** 명령 → 실제 출력 → 설명을 반복한다.
6. **주의, 함정, 언제 쓰지 말까:** 실제로 겪은 에러 원문과 회복 방법을 적는다.
7. **마무리:** 요약, 다음 첫 행동, 정리(cleanup), 참고 링크로 끝낸다.

**변형:** 위키형(65~67)은 서론이 없고 created/updated 날짜를 쓰며, 낡은 내용은 Deprecated 섹션으로 격리한다. 이 외에 런북형(121), 레시피 모음형(84), 검증·체험형(17, 101)이 있다.

**필수 체크리스트**
- [ ] 모든 핵심 명령 뒤에 실제 출력이 텍스트로 있다. (51, 65, 101, 121 / 반례 X1)
- [ ] 바뀔 수 있는 수치(가격, 한도, 기본값)에 출처와 확인 날짜가 있다. (반례 62)
- [ ] 버전을 고정했다. `latest` 태그나 버전 없는 설치 명령을 쓰지 않는다. (17, 51 / 반례 X1, 121의 이미지)
- [ ] 공식 문서와 실제 동작이 다른 지점을 표시했다. (15, 17, 66)
- [ ] 갱신하는 글이면 Updated 날짜와 변경 이력을 남겼다. (16, 66 / 반례 67)

### R 리서치·리뷰

**뼈대**
1. **원문 식별:** 제목, 저자나 기관, 연도, 링크를 맨 앞에 둔다.
2. **동기와 선별 범위**
3. **원문의 한계를 먼저 밝힘:** 표본, 재현 가능성, 빠진 실험을 요약보다 앞에 적는다.
4. **배경 개념**
5. **본문:** 원문 구조를 따르거나, 필자가 고른 발견 순서로 쓴다.
6. **필자 해석:** 별도 섹션이나 문장 표지로 원문 내용과 분리한다.
7. **마무리:** 교훈과 원문 탐색 권유로 끝낸다.

**필수 체크리스트**
- [ ] 원문 주장과 내 해석을 문장 술어나 헤딩으로 구분했다. (96, 69, 99, 44)
- [ ] 하위 그룹이나 작은 표본의 결과를 전체로 일반화하지 않았다. 제목이 본문보다 강하지 않다. (반례 63)
- [ ] 옮긴 수치마다 출처와 측정 조건을 적고, 집계 방식이 바뀌었는지 확인했다. (18, 44 / 반례 60)

## 6. 문체 관찰

- **어미:** 반말(~다)이 다수였다. C 유형에서는 15편 중 11편이 반말이다. 존댓말은 Dale Seo, benelog, 교재형(94), 가이드 일부에서 쓰였다. 어미는 신뢰와 상관이 없었으므로, 스킬에서는 사용자의 선택으로 둔다.
- **1인칭:** 반말 글은 "필자"를 쓰거나 1인칭을 생략했다. 존댓말 글은 해석을 밝히는 문장에서만 "저는"을 썼다.
- **길이:** 신뢰도가 높은 글은 대부분 길었다(1만 자 이상). 짧은 글은 근거가 얇은 경향이 있었다(13, 64). 다만 짧은 메모형(97)은 미해결 상태를 명시하면 허용됐다.
- **유머와 감정:** 근거 밀도가 높으면 신뢰를 해치지 않았다. 감정 서술이 반복되면 근거를 희석했다(113).

## 7. 스킬 설계 시사점

1. **구성:** 공통 원칙(§1) → 유형 판별 → 유형 템플릿(§3) → 분야 체크리스트(§4) → 안티패턴 검사(§5) 순서로 동작하게 한다.
2. **유형 판별 질문:** 사용자의 소재로 유형을 정하는 질문을 둔다. 예: "실제 장애가 있었는가?"(T), "직접 측정했는가?"(H), "입장을 펴는가?"(A).
3. **증거 수집 단계를 글쓰기보다 먼저 둔다.** P1과 P3을 지키려면 환경 정보, 실제 출력, 측정값을 먼저 모아야 한다. 증거가 없는 섹션은 "미검증"으로 표시하게 한다.
4. **AI 작성 고지 규칙:** 스킬로 쓴 글에는 AI 도움을 받았다는 고지와 함께, 사람이 직접 확인한 범위를 적는 절을 기본으로 넣는다(P10). 분석한 샘플 중 이것까지 한 글은 없었다.
5. **남은 공백**
   - **AI × T가 2편뿐이다.** AI 트러블슈팅 템플릿은 일반 T 템플릿에 AI 분야 체크리스트를 결합해 쓰고, 나중에 샘플을 보충한다.
   - **INF 샘플은 17편이다.** 유형별로 보면 칸마다 표본이 적다.
