읽기 상태: 15편 모두 읽음. 2와 40은 본문 끝부분(마무리)을 직접 확인하지 못했다. 2는 목차로 확인했고 40은 앞부분만 읽었다.

### #2 VO vs DTO: 정의와 용어 혼용의 역사 (benelog, BE)
| 항목 | 내용 |
|---|---|
| 유형/분야 | C / BE 확정. 용어 정의를 1차 문헌으로 추적하는 "용어사(史) 해설" 하위형 |
| 도입 | 실무에서 getter/setter 객체를 VO라고 부르는 관행을 먼저 짚고, 그 관행이 혼란을 부른다는 주장을 리드 문단 한 곳에서 밝힌다. 목차를 앞에 둔다 |
| 구조 | VO 정의 → (하위) 불변성의 위상: 정의 요건인가 바람직한 설계인가 → DTO 정의 → Core J2EE Patterns 초판 VO와 개정판 TO → 데이터 운반 객체를 VO라고 부를 때의 비용 → 참고 자료. 정의에서 출발해 역사, 실무 비용 순으로 간다 |
| 근거 | 1차 문헌 밀도가 매우 높다. Fowler(PoEAA 쪽수, bliki, c2 wiki), Evans DDD Reference, Effective Java Item 10/11/17, JEP 395/401/169, MS .NET 문서, Wikipedia, Vernon IDDD, 국내서 쪽수, Cambridge Dictionary를 인용하고 원문과 번역을 함께 싣는다. jshell/AssertJ로 직접 만든 예제 코드도 있다 |
| 설명 기법 | 개념 대비(식별성과 동등성). 반례 코드로 Date 별칭 버그와 LocalDateTime 해법을 보여 준다. should와 must를 사전으로 구분한다. "음주운전 금지를 운전자의 정의에 넣을 것인가" 비유. 같은 패턴의 세 이름을 등식(VO=TO=DTO)으로 정리한다 |
| 불확실성 | 매우 명시적이다. "저는 ~로 읽습니다"처럼 해석을 사실과 분리한다. 반대 입장(불변성을 정의로 보는 MS, Wikipedia, Vernon)을 목록으로 공정하게 제시한다. JEP 401의 상태를 "2026년 8월 현재"로 시점을 박는다. 개칭 동기에는 "~로 보입니다"라고 추정임을 표시한다 |
| 마무리 | 실무 비용과 제안(역할별 접미어 분리), 그리고 분류된 참고 자료 목록 |
| 문체 | 존댓말(합니다체). 1인칭 "저는"은 해석에서만 쓴다. 매우 길다(15,000자 이상) |
| 눈에 띄는 기법 | (1) 권위자 문장 하나를 앞뒤 문맥까지 인용해 "정의인가 지침인가"를 판정한다. 원문 정독 자체를 논증으로 쓴다. (2) 반대 견해를 같은 형식의 목록으로 나란히 두고 나서 자기 입장을 밝힌다 |

### #5 IEEE 754 부동소수점 오차와 Java의 대안 (benelog, BE)
| 항목 | 내용 |
|---|---|
| 유형/분야 | C / BE 확정. 원리 + 사고 사례 + 선택 가이드가 결합한 형태 |
| 도입 | 0.1을 정확히 표현할 수 없다는 사실을 한 문단으로 요약하고 글의 범위(원리, 위험, 대안)를 예고한다. 번호 붙은 목차가 있다 |
| 구조 | 1 코드로 확인하는 오차(현상) → 2 binary64 비트 구조와 0.1 저장 과정(원리) → 3 장애 사례(NEIS 2011, 패트리어트 1991) → 4 대안(BigDecimal, 정수) → 5 선택 기준 → 6 도메인 라이브러리 → 7 참고 자료. 현상, 원리, 영향, 해법, 판단 순으로 간다 |
| 근거 | IEEE 754 판본 이력, Effective Java Item 60, Stripe API 문서, GAO 보고서(서적 경유), 신문 기사 여러 건(인용 기사를 문장마다 표시), Db2 문서, Lawrey의 JMH 벤치마크(측정 연도 명시), JOL 실측(JDK 25 환경 명시). jshell 재현 코드가 풍부하다 |
| 설명 기법 | 단계별 예시(2를 거듭 곱해 지수와 가수를 구하고 16진수 3fb999...a로 검증). 기존 블로그(우아한형제들) 코드의 한계를 경계값 16,777,217로 반증하고 고친 버전을 보여 준다. 비교표(BigDecimal과 long) |
| 불확실성 | "나이스의 실제 계산식이 아니라 원리를 보여 주는 예", 패트리어트는 부동소수점이 아니라 고정소수점이었다는 점, 벤치마크는 2014년 값이라 지금은 다를 수 있다는 점, long과 직접 비교한 것은 아니라는 점을 꼼꼼히 밝힌다 |
| 마무리 | 팀 규칙을 단순하게 문서화하라는 실무 지침, 금액 로직을 메서드로 분리해 테스트하라는 조언, 참고 자료 |
| 문체 | 존댓말. 1인칭은 거의 없다. 매우 길다 |
| 눈에 띄는 기법 | (1) 추상 원리를 실제 국내 사고(NEIS)에 연결하고 동일 현상을 재현 코드로 보여 준다. (2) 인용한 벤치마크마다 측정 시점, 환경, 비교 대상의 한계를 바로 옆에 붙인다 |

### #27 테스트 데이터 초기화에 @Transactional 사용하는 것에 대한 생각 (향로, BE)
| 항목 | 내용 |
|---|---|
| 유형/분야 | **가설 C → 재분류 제안: 의견/논증(입장 표명)형.** 분야 BE 확정 |
| 도입 | 맥락은 커뮤니티 논쟁이다. 재민님 영상과 토비님 페이스북이 서로 다른 의견을 냈고, 저자는 "반대한다"고 언급된 당사자로서 입장을 정리한다. 개념을 설명하는 도입이 아니라 입장을 표명하는 도입이다 |
| 구조 | 1 Spring Team은?(반대 측 최강 근거를 먼저 제시) → 2 발생할 수 있는 문제점(2-1~2-4 사례 4개) → 3 마무리(조건부 결론 + 팀 규칙 철학 + 자기 의심) → 번외: 대안(CleanUp 빈) |
| 근거 | spring-data-jpa 저장소의 실제 테스트 코드(링크). GitHub 예제 저장소(Kotlin). 사례마다 실패 테스트와 성공 테스트 쌍(직접 만든 재현). 공식 문서나 스펙 인용은 없다 |
| 설명 기법 | 대조 실험 쌍: `@Transactional` 테스트(실패)와 명시적 초기화 테스트(성공)를 같은 구조로 나란히 둔다. `@Order`로 "다음 테스트에서 DB가 비었는지" 검증하는 장치. 실행 결과는 스크린샷(본문 텍스트에서는 누락) |
| 불확실성 | 매우 솔직하다. 2-1에서 "팀 규칙만 잘 정하면 발생 여지가 거의 없다"고 자기 사례의 약점을 인정한다. 비동기 insert는 "실제로는 거의 없다"고 밝힌다. 결론 끝에 주류가 반대편일 수 있다는 자기 의심과 재작성 가능성을 남긴다 |

**논증 구조 상세 (요청 사항)**
1. **주장의 위치:** 제목은 "생각"이고 명시적 주장은 2절 첫 문장("그럼 나는 왜 반대할까?")에서 나온다. 주장보다 반대 측 근거가 먼저 온다.
2. **반론 선제 제시(steelman):** 1절에서 반대 측의 가장 강한 근거, 즉 "스프링 팀 자신이 테스트에 `@Transactional`을 쓴다"를 저자가 먼저 꺼내고, 그것이 "스프링 팀에서도 권장하는 방법"이라고 인정한다.
3. **근거의 형식:** 추상 논변 대신 반례 4개(의도치 않은 트랜잭션, REQUIRES_NEW, 비동기, AFTER_COMMIT 리스너)를 든다. 각 반례는 [시나리오 → @Transactional 테스트 → 실패 결과 → 원인 한 줄 → 명시적 초기화 테스트 → 성공] 템플릿을 반복한다. 반례마다 "격리가 깨진다"는 같은 함의로 수렴한다.
4. **근거 강도의 자기 평가:** 2-1은 팀 규칙으로 거의 막을 수 있다고 인정하고, 2-3은 실제로 드문 상황이라고 밝힌다. 반례의 현실성을 스스로 할인한다.
5. **결론의 범위 축소:** "쓰면 안 된다"가 아니라 "안티 패턴은 아니다, 다만 트랜잭션 관련 코드에서는 주의"로 좁힌다. 일반 명제를 조건부 명제로 바꾼다. 같은 이유로 `@DataJpaTest`로 확장한다.

7. **자기 반박 여지:** 마지막 인용 블록에서 주류(스프링 팀, 토비, 영한)가 반대편이라는 점을 스스로 상기하고 "다시 쓰게 될지도 모른다"고 남긴다.
8. **대안 제시:** 비판만 하지 않고 번외에서 대체 구현(TRUNCATE 기반 CleanUp)을 준다. 다만 그 대안의 전제(FK 미사용 등)를 명시하며, 이 전제 자체도 논쟁적이다.

- **원칙화:** 논쟁적 주장을 쓸 때는 (a) 상대의 가장 강한 근거를 먼저 인정하고, (b) 재현 가능한 반례를 대조 실험 쌍으로 제시하고, (c) 결론을 조건부로 좁히고, (d) 최종 선택이 기술 사실이 아니라 가치(팀 운영 철학)에서 온다는 점을 밝힌다.

### 2.2 변형 패턴
- **질문 목차형(24, 45 일부):** 섹션 헤딩을 독자 질문으로 만든다. 마지막 질문을 "써야 하나?"로 둔다.
- **증상 귀납형(42, 38):** 서로 다른 증상 여러 개를 하나의 원리로 묶고, 그 원리로 증상을 재해석한다.
- **발명 서사형(41, 40):** "이 문제를 풀려면 무엇이 필요할까"를 따라 개념을 재발명한다. 수미상관으로 처음의 난해한 정의로 돌아온다.
- **문헌 추적형(2):** 정의를 1차 문헌의 문장 단위까지 정독해 판정한다. 반대 문헌도 나란히 둔다.
- **원리→사고→처방형(5):** 원리를 실제 장애 사례에 연결하고 선택 가이드로 끝낸다.
- **버전 진화형(32, 64):** JDK 버전, API 세대별로 무엇이 바뀌었는지를 따라간다.
- **소스 해부형(35):** 사용법에서 시작해 내부 자료구조와 설계 주석으로 내려간다. "왜 이렇게 생겼나" 소제목을 반복한다.
- **분류 체계형(45):** 기법의 2단 분류 트리가 곧 목차다. 각 기법의 한계가 다음 기법으로 넘어가는 다리가 된다.
- **논증형(27, C에서 이탈):** 반론 선제 제시 → 반례 실험 → 조건부 결론 → 가치 전제.

- 단순화를 선언하고 나중에 회수한다(40 8비트 체크섬, 41 "모나드는 박스가 아니다", 45 5ms 휴리스틱 고백).
- 날짜가 있는 상태 서술("2026년 8월 현재" 2, Updated 표기 13).
- AI 생성을 공개한다(64). 투명성은 높이지만 근거 부족을 상쇄하지는 못한다.

### 2.5 신뢰를 떨어뜨리는 안티패턴
- 근거 없는 전망과 과장("잠재력은 무한", "새로 배울 기술이 사실상 없다" 13).
- 1차 출처 없이 매끈한 일반론만 있다. 개인 경험과 실측이 없다(64).
- 오탈자와 미완 문장(13). 신뢰 신호를 직접 깎는다.
- 결과를 스크린샷으로만 보여 주면 텍스트 추출과 검색에서 사라진다(27, 32의 이미지 코드). 재현성과 접근성이 떨어진다.
- 동기 부여 없이 정의부터 시작하는 도입(32). 왜 읽어야 하는지가 늦게 나온다.
- 대안의 전제를 독자가 따르기 어려운 경우(27 "FK 미사용"). 전제를 밝히긴 했지만 그 전제 자체를 논증하지 않는다.

### 2.6 스킬 체크리스트 후보
1. **도입에 독자가 이미 겪은 증상, 에러 메시지, 의문을 하나 두고, 글이 답할 질문 목록이나 범위를 예고한다.** (24, 38, 45, 14, 39, 42)
2. **정의 직후 "가장 작은 재현"을 둔다.** 코드, 명령, 와이어 메시지 중 하나로, 독자가 그대로 실행할 수 있어야 한다. (5, 24, 13, 14, 38)
3. **개념이 왜 존재하는지를 이전 방식의 한계나 역사로 설명한다.** 정의만 나열하지 않는다. (35, 40, 24, 41, 64, 2)
4. **흔한 오해를 하나 이상 명시적으로 교정한다.** "~로 알려져 있지만 실제로는"처럼 쓴다. (39, 38, 45, 24, 35)
5. **모든 수치에 측정 환경, 시점, 비교 대상의 한계를 붙인다.** 남의 수치를 인용할 때도 같다. (5, 32, 24, 35)
6. **표준·공식·소스 근거를 분야 관습에 맞게 단다.** NET은 RFC, FE는 스펙과 MDN 각주, Java는 JEP·소스·명저 Item. 해석과 사실은 문장 단위로 구분한다. (2, 38, 24, 35, 42)
7. **비유를 쓰면 그 비유가 깨지는 지점도 밝힌다.** 단순화한 부분(축소 예제, 휴리스틱 값)은 단순화라고 선언한다. (41, 40, 45, 14)
8. **적용 범위와 반대 조건을 쓴다.** "이럴 땐 이 기법이 필요 없다"나 "써야 하는가"를 다루는 절을 둔다. (24, 32, 64, 5)
9. **마무리에 독자가 들고 갈 진단 질문이나 팀 규칙 한 줄을 남긴다.** 요약에서 끝내지 않는다. (14, 42, 5, 27)
10. **논쟁적 주장이 섞이면 반대 측의 가장 강한 근거를 먼저 인정하고, 결론을 조건부로 좁히고, 가치 전제를 밝힌다.** (27, 2)

### 2.7 문체 분포
- 반말(~다)은 11편(24, 27, 32, 35, 38, 39, 40, 41, 42, 45, 64)이고, 존댓말은 4편(benelog의 2와 5, Dale Seo의 13과 14)이다. 반말 글은 "필자" 또는 1인칭을 생략하고, 존댓말 글은 "저는"을 해석에서만 쓴다.
- 길이는 대부분 길다(1만 자 이상이 11편). 짧은 글(13, 64)은 근거가 얇은 경향이 있다.
- 유머와 밈은 Evan Moon 계열에 집중되고, benelog와 망나니개발자는 건조하다. 유머가 있어도 신뢰는 근거 밀도로 결정된다.
