### 74. HTTP 캐싱 (김정환)
| 항목 | 내용 |
|---|---|
| 확정 유형/분야 | C / NET (FE와 겹침), 확정 |
| 도입 | 캐시를 정의하고 "성능을 좌우한다"로 필요성을 밝힌 뒤, 서버가 정책을 정하고 브라우저가 따른다는 큰 그림을 먼저 줌 |
| 구조 | 서론 → 시간 기반(Last-Modified) → 내용 기반(ETag, 앞 방식의 한계로 동기 부여) → 캐시 제어(Cache-Control, Expires, Vary, meta 태그) → 실무 전략(HTML이 아닌 파일 / HTML 파일) → 결론(헤더 목록 + 판단 흐름) → 참고. **단순한 것에서 정교한 것으로, 원리에서 실무로** |
| 근거 | 직접 만든 Node 서버 코드(예제 저장소 링크), 헤더가 등장한 HTTP 버전 표기, RFC 2068 한 문장 인용, 실제 CDN(core-js, react)의 max-age 값, 스택오버플로우, 책 2권(HTTP 완벽 가이드, 리얼월드 HTTP), MDN, web.dev |
| 설명 기법 | **요청·응답 헤더 옆에 말풍선 같은 주석을 달아 대화로 의인화**("이 날짜 이후로 바뀐 게 있나요?"). 앞 방식의 한계 → 다음 방식이라는 진화 서사. 흔한 오해 바로잡기(meta 태그 캐시 설정은 좋지 않다). 결론에 결정 트리형 요약 |
| 불확실성 | Vary가 정의된 버전을 "(?)"로 남김. "~라고 한다"로 2차 출처임을 표시 |
| 마무리 | 헤더 요약 + 동작 흐름 재정리 + 주의("캐시를 설정할 때는 신중해야") + 참고 목록 |
| 문체 | 반말, 중간 이상 길이 |
| 눈에 띄는 기법 | **원칙: 프로토콜 해설은 헤더 교환을 대화체 주석으로 의인화하면 상태 전이가 직관적으로 보인다.** **원칙: 새 메커니즘은 앞 메커니즘의 구체적 한계(1초 해상도, 저장만 해도 바뀌는 수정일)로 동기를 부여한다** |

### 76. 테스트가 관리하는 트랜잭션: 향로 님의 @Transactional 글을 읽고 (토비)
| 항목 | 내용 |
|---|---|
| 확정 유형/분야 | **C/E 혼합. 응답 논평(반론 에세이)이 주이고 개념 해설은 기반으로 깔림** / BE, 확정 |
| 도입 | 논쟁의 계보(재민 님 영상 → 토비의 페이스북 → 향로 글)를 설명하고, 상대가 예제 코드까지 만들어 준 데 감사를 표함. 자기 입장("나는 롤백 테스트를 주로 쓴다")을 처음부터 밝힘 |
| 구조 | 계보·감사 → **스프링 테스트의 트랜잭션 관리(공통 기반을 먼저 세움)** → "우리는 트랜잭션을 테스트하는가?"(쟁점 재구성) → 상대 사례별 반론(REQUIRES_NEW → 비동기 메서드 → TransactionalEventListener) → 테스트에 대한 생각 정리(동의 표명 + 상대 방식의 비용: 테이블 초기화 성능, 메모리 DB, FK 제거, 시드 데이터) → 맺음 인사 → 새로 안 사실(@BeforeTransaction 파라미터) → 레퍼런스 코드 |
| 근거 | 스프링 레퍼런스 문서(TransactionalTestExecutionListener, TestTransaction), 스프링 1.1·Epril 세미나라는 **역사적 맥락(설계 의도 증언)**, 수십 년의 장애 경험. 코드는 마지막에 레퍼런스에 있는 예제 하나뿐("코드 한 줄 없이 말로만 떠들었더니") |
| 설명 기법 | 아래 "논증 방식" 참고. 수사 의문문을 연달아 던짐. 속담 비유("빈대 잡으려다 초가삼간") |
| 불확실성 | "그럴 수도, 아닐 수도 있겠다"처럼 조건부로 양보함. 자신도 트랜잭션은 "거의 테스트하지 않는다, 사실은 테스트 못한다"고 인정 |
| 마무리 | 존중·동의 표명 → 자기 권고(기본은 @Transactional, 주의점을 숙지하고 필요하면 커밋 테스트) → 감사·대화 제안 → 덤 정보 |
| 문체 | 반말, 구어체, 1인칭 강함, 사담("부러진 손가락"). 긴 글 |
| 논증 방식 (상세) | 1) **인용 방식:** 원문 링크(카드)만 걸고 문장은 거의 인용하지 않는다. 상대의 *예제 코드*를 구체적 대상으로 지목해("CompletableFuture를 async로 만들고 get()으로 블로킹") 문장 대신 사례를 반박한다. 2) **공통 기반 먼저:** 반론 전에 프레임워크의 공식 동작과 주의점 3가지(전파 속성, ThreadLocal 바인딩, 경계 확장에 따른 거짓 음성)를 정리한다. 상대가 보인 실패 사례를 "문서 첫머리에 나오는 기본 상식" 범주로 옮겨 놓는 효과가 있다. 3) **쟁점 재정의:** "우리는 트랜잭션을 테스트하는가?"라는 상위 질문으로, 어느 쪽 방식이든 트랜잭션 버그를 잡지 못한다는 공통 한계를 보인다. 상대 주장의 우위 근거를 약화시킨다. 4) **사례별 3단 반론:** (a) 그 상황이 실제로 얼마나 흔한가, (b) 애초에 그 코드나 테스트 설계가 맞는가, (c) 더 싼 대안(커밋 테스트 후 정리, @Async를 mock 처리하고 직접 호출)이 있다. 결론은 "전체를 포기할 이유는 없다"는 비례성 논증이다. 5) **상대 방식의 비용 제시:** 성능, 메모리 DB와 실제 DB의 차이, FK 제거 위험, 시드 데이터 불편. 6) **존중과 양보:** "상당부분 동의한다", 상대 스타일 팀이면 그대로 가겠다는 양보로 인신공격으로 읽히지 않게 한다. 7) **권위의 근거:** 스프링 초기부터 이 기능을 써 온 역사 증언을 쓴다(독자가 검증하기는 어려움) |
| 눈에 띄는 기법 | **원칙: 반론 글은 상대 주장을 공격하기 전에 양쪽이 동의할 공식 동작부터 정리하고, 쟁점을 한 단계 위의 질문으로 재정의한 뒤, 사례마다 "빈도, 설계 적절성, 더 싼 대안"을 따져 비례성을 논한다.** **원칙: 존중과 부분 동의를 명시해 논쟁을 대화로 유지한다** |

### 80. 인터넷이 동작하는 아주 구체적인 원리 (parksb)
| 항목 | 내용 |
|---|---|
| 확정 유형/분야 | C / NET, 확정 |
| 도입 | 부제 "학교에서 구글에 접속하는 과정"이라는 **독자가 매일 하는 구체적 시나리오** 하나로 시작. 서두에서 가정과 단순화를 먼저 선언 |
| 구조 | 영문 헤딩 목차 → 학교 네트워크 지도 → WLAN·DHCP·UDP·IP → Ethernet·DNS·ARP → 도메인 내 라우팅·DNS 계층 → TCP·TLS·HTTP → References. **패킷이 실제로 이동하는 시간 순서이자 하위 계층에서 상위 계층으로** |
| 근거 | Kurose & Ross 교과서(7판)의 "웹 요청의 하루" 시나리오를 한국 맥락(KT, warning.or.kr)으로 각색, Cloudflare TLS 문서, IEEE 802.11/802.3 표준 이름, TeleGeography 해저 케이블 지도 |
| 설명 기법 | **ASCII 다이어그램으로 매 단계 패킷의 실제 필드값(src 0.0.0.0, 255.255.255.255, MAC, transaction ID)을 보여 줌.** 같은 지도를 확장해 가며 반복. 가상의 구체적 주소값으로 일관되게 추적 |
| 불확실성 | 서두에 주소, 망 구조, 프록시·캐시 생략이 모두 "간소화 또는 가정"이라고 밝힘. 결말 부분에서 방화벽·로드밸런서 생략도 언급 |
| 마무리 | 구글이 브라우저에 뜨는 장면으로 서사를 닫고 References, CC 라이선스 |
| 문체 | 반말, 1인칭 없음, 교과서 톤. 긴 글 |
| 눈에 띄는 기법 | **원칙: 거대한 개념은 독자의 일상 행위 하나를 끝까지 추적하는 시나리오로 엮고, 같은 가상 값으로 일관되게 따라간다.** **원칙: 단순화 가정을 글 첫머리에 한꺼번에 선언한다** |

## 2. 유형 종합 (14편 기준, 단 68·73은 표본으로서 약함)

### 2.1 공통 뼈대
대부분(71, 72, 74, 80, 81, 85, 86, 94, 98, 120)이 따르는 순서는 다음과 같다.

1. **문제 또는 동기 한 단락:** 익숙한 방식이 깨지는 상황(85, 86), 성능 격차(81), 일상 시나리오(80), 실무에서 막힌 경험(98), 독자가 아는 API(71, 72). 길어야 3문단이다.
2. **큰 그림 또는 정의:** 정의 한 줄과 전체 구조(그림이나 목차)를 먼저 보인다(74, 94, 120).
3. **메커니즘 단계별 전개:** 시간 순서(요청과 패킷의 이동: 72, 80, 120), 호출 순서(71), 진화 순서(앞 방식의 한계 → 다음 방식: 74, 85, 86, 94) 중 하나를 축으로 삼는다.
4. **구체 예제와 관찰:** 작은 표, 손계산 시뮬레이션, 실제 헤더·패킷·덤프.
5. **한계, 트레이드오프, 비교:** 비슷한 기술과의 비교(72 vs React.lazy, 94 vs CNN·RNN, 98 vs NVLink), 해법의 한계(85, 86).
6. **마무리:** 요약 목록(71, 74) 또는 실무 적용(74, 81). 요약 없이 References로 끝나는 글도 절반가량 된다(85, 86, 94, 98, 120).

### 2.2 변형 패턴
| 변형 | 샘플 | 특징 |
|---|---|---|
| 코드 리딩형 | 71 | 진입점 API → 내부 객체로 내려감. 시그니처 발췌, 설계 의도 추측 표시 |
| 시나리오 추적형 | 80 | 일상 행위 하나를 끝까지 따라감. 가상 값으로 일관되게 추적 |
| 진화 서사형 | 74, 85, 86, 94 | "기존 방식의 한계 → 새 방식"을 반복 |
| 교재형 | 94, (73) | 존댓말, 그림·수식 번호, 장 간 상호 참조. 요약은 다음 장으로 미룸 |
| 구현 해부형 | 120 | 버전 고정, 재현 환경, 설정 덤프로 검증 |
| 학습 일지형 | 98, 86 | 개인 계기와 사담, 용어집. 출처가 느슨함 |
| 역사·에세이 혼합형 | 82 | 1차 문헌 각주, 저자 입장으로 끝남 |

| 노트·목차형 | 68, 73 | 독립된 해설 글이 아님 |

### 2.3 분야별 근거 관습
- **CS (81, 68):** 교과서(Patterson & Hennessy, Silberschatz)와 손계산 예제, 수식. 서지는 학술 형식이다.
- **NET (74, 80, 73):** 교과서(Kurose & Ross, HTTP 완벽 가이드), RFC 문장, MDN/web.dev, IEEE 표준 이름. **직접 만든 서버 코드나 패킷 필드값**으로 관찰하게 한다.
- **FE (71, 72, 82):** 라이브러리 소스 코드와 직접 만든 예제가 중심이다. 공식 문서 인용은 적다. 82만 예외로 1차 문헌 각주를 단다.
- **BE (85, 86, 76):** 책 한 권(대규모 시스템 설계)과 Redis 공식 문서, 스프링 레퍼런스. 장애 시나리오로 논증한다. 링크 없이 "공식 문서에 따르면"이라고만 하는 경우가 있다(86).
- **AI (94, 98):** 교재형은 논문 그림과 장난감 수치를 쓴다. 인프라 학습기는 업계 블로그와 수치를 쓰지만 수치 출처가 약하다.
- **INF (120):** 버전 고정, 재현 가능한 명령, 설정 덤프, GitHub 이슈와 제안서(KEP 비슷한 문서)까지 인용한다. **근거 밀도가 가장 높다.**

### 2.4 신뢰를 높이는 기법
- 단순화와 가정을 글 첫머리에 한꺼번에 선언한다(80).
- 이해하지 못했거나 확실하지 않은 부분을 그 자리에서 표시한다(72, 81, 71은 추측 표시).
- 분석 대상 버전을 고정하고 재현 환경을 준다(120).
- 앞 방식의 구체적 한계로 새 방식의 동기를 만든다(74, 85, 94).
- 해법 다음에 트레이드오프나 한계를 붙인다(85, 82, 98).
- 작은 규모로 줄인 수치 예제를 단계별로 돌린다(81, 85, 94).
- 1차 문헌을 각주로 단다(82). 반대 입장을 직접 다룬다(76, 82).
- 마지막에 적용 범위를 한정한다(81: 컴파일러가 해 준다).

### 2.5 신뢰를 떨어뜨리는 안티패턴
- 논쟁적인 기술에서 알려진 반론을 빠뜨린다(86: Kleppmann과 펜싱 토큰 누락).
- 문제만 제기하고 결론 없이 끝낸다(86).
- 출처 없는 수치("연구에 따르면", 대역폭 수치)를 쓴다(86, 98).
- "공식 문서에 따르면"이라고만 하고 링크를 달지 않는다(86).
- 오탈자가 코드 식별자에 섞인다(71: excuteFetch, 74: If-Modifed-Since). 독자가 실제 API 이름을 의심하게 된다.
- 개조식 목차만 있고 설명이 없다(73).
- 독자가 검증할 수 없는 권위(역사 증언)에 기댄다(76). 효과는 있지만 공식 문서로 보강하는 편이 낫다.

### 2.6 스킬 체크리스트 후보
1. **도입 3문단 안에 "기존 방식이 깨지는 구체적 상황"이나 "독자가 이미 쓰는 것"을 보였는가?** (85, 86, 81, 98, 71, 72)
2. **메커니즘 전개의 축(시간 순서, 호출 순서, 진화 순서) 하나를 정하고 끝까지 지켰는가?** (80, 71, 72, 74, 94)
3. **글 전체를 관통하는 예제 하나(예문, 가상 IP, 작은 캐시)를 정해 반복해서 썼는가?** (94, 80, 81)
4. **추상 설명마다 독자가 손으로 따라갈 수 있는 작은 수치 예제나 관찰 가능한 출력(헤더, 패킷, 덤프)이 붙어 있는가?** (85, 81, 74, 72, 120)
5. **단순화, 가정, 생략, 대상 버전을 명시했는가? 모르는 부분은 그 자리에서 표시했는가?** (80, 120, 72, 81)
6. **해법 다음에 한계와 트레이드오프, 알려진 반론을 다뤘는가?** (85, 82, 86은 반례)
7. **비슷한 기술과의 비교(축 2~3개)를 넣었는가?** (72, 94, 98)
8. **수치와 주장마다 출처 링크가 있는가? 1차 문헌(RFC, 논문, 공식 문서)을 우선했는가?** (82, 120, 74. 반례 86, 98)
9. **마지막에 "그래서 실무나 내 코드에서는"과 적용 범위를 제시했는가?** (74, 81)
10. **반론 글이라면 공통 기반을 먼저 정리하고, 쟁점을 재정의하고, 사례별로 비례성을 따지고, 부분 동의를 명시했는가?** (76)
