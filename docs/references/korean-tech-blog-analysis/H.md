### 1. Java에서 외부 프로세스를 실행하기: JDK 25와 Linux 6.x 기준 (benelog) — 유형 H, 분야 BE (가설 유지, 해설(T) 성격이 섞임)
- **도입:** 리드 요약을 먼저 두고 목차가 이어집니다. 범위를 "JDK 25와 Linux 6.x 기준"으로 선언하고, 바로 **환경표**(OS·커널, 아키텍처, glibc, JDK 빌드, 라이브러리 2종 버전)와 예제 저장소 링크를 제시합니다.
- **구조:** API 차이 → 기본 옵션의 한계 → 파이프 교착(재현 → 해결) → stdin과 EOF → 시간제한·종료 정책 → 후손 프로세스 정리(프로세스 그룹, cgroup) → 라이브러리 2종 비교 → Linux 프로세스 생성 방식과 측정 → 마치며 → 참고 자료.
- **근거:** 예제마다 *데모 파일명 → 코드 → "실행 결과" 블록 → 해석* 순서를 지킵니다. pipe(7) 매뉴얼로 버퍼 크기를 확인하고, 그 값을 고정 한계로 가정하지 말라고 단서를 붙입니다. SpawnBench는 힙 크기 3단계에서 워밍업 5회 후 30회 평균을 내고, 이 측정을 두 번 반복했습니다. Javadoc 원문은 인용한 뒤 번역해 붙였습니다.
- **불확실성:** 측정값은 환경과 힙 크기에 따라 달라지므로 보편적인 배율이 아니라고 밝힙니다. dash와 bash의 차이처럼 셸에 따라 결과가 갈리는 경우도 따로 보고합니다. JDK 27 변경은 "개발 버전"이라고 구분합니다.
- **마무리:** 요약(출력 처리, 시간제한, 종료 정책을 함께 설계할 것)에 권장 사항(zt-exec 사용, 기본값 POSIX_SPAWN 유지)을 더합니다.
- **형식:** 환경표와 API 비교표가 있고, 코드 블록마다 파일명 캡션을 붙였습니다. 결과는 별도 블록으로 보여 줍니다.
- **문체:** 합니다체입니다. 1인칭은 적게 씁니다. 매우 긴 글입니다(2만 자 이상으로 추정).
- **기법:** ① 실행 결과를 증거 블록으로 따로 둡니다. 코드 블록과 출력 블록을 분리하고, 출력 바로 뒤에 해석 한 문단을 붙입니다. ② 기능마다 도입된 JDK 버전을 괄호로 표기해서 독자가 자기 환경에 맞는지 판단할 수 있게 합니다.

### 3. GitHub Actions 워크플로 튜닝: 저장소 다섯 곳의 적용 사례 — H / INF (가설 유지)
- **도입:** 앞 글(기법 정리)의 후속편이라고 밝히고, 이 글은 결과에 집중한다고 범위를 나눕니다. 대상 저장소, 러너 사양(4 vCPU / 16GB), 측정 날짜를 명시합니다.
- **구조:** 저장소마다 번호를 붙인 섹션 5개(적용한 것 → 실제 로그나 설정 → 수치 → 해석) → 정리표 → 참고 자료.
- **근거:** `gh run view`로 뽑은 단계별 소요 시간을 원문 그대로 보여 줍니다. 캐시 실험은 두 번 실행해 1회차와 2회차를 표로 비교합니다. 공개 저장소 경로를 그대로 적었습니다.
- **불확실성:** 두 번만 비교했기 때문에 러너 성능 편차가 섞였을 수 있다고 밝힙니다. 그러면서도 두 실행에서 일관되게 나온 부분(캐시 저장 비용)은 따로 짚습니다. **예상과 다른 결과**(정석으로 알려진 캐시가 이득이 없었고, 병목이 빌드가 아니라 업로드였다)를 글의 핵심 메시지로 끌어올립니다.
- **마무리:** 정리표(저장소, 적용한 것, 결과)를 두고 "측정이 먼저"라는 교훈 한 문단으로 끝냅니다. AI와 함께 썼다고 밝힙니다.
- **형식:** YAML 블록에 파일 경로 캡션을 붙였습니다. 표는 2개입니다.
- **문체:** 합니다체입니다. 1인칭은 "제 저장소" 정도로만 씁니다. 중간 길이입니다.
- **기법:** ① 사례마다 결과 한 줄을 정리표로 모아, 글 전체를 표 하나로 다시 읽을 수 있게 합니다. ② 표본이 작다는 한계와 그래도 일관되게 관측된 사실을 한 문단 안에서 나란히 적습니다.

### 7. Istio의 재시도 정책과 관련 메트릭 살펴보기 (outsider) — H / INF (가설 유지)

- **구조:** 개념(defaultHttpRetryPolicy, 공식 설명 번역) → 데모(kind 클러스터, Istio 설치, 동작 확인) → 소감과 저장소.

- **불확실성:** 개선이 목적이 아니라 동작을 확인하는 실험이었다고 범위를 정합니다. 구분해 보고 싶었던 케이스는 방법을 찾지 못했다고 실패를 기록하고, 관련 메트릭은 더 검토해야 한다고 남깁니다.
- **마무리:** 무엇을 알게 됐는지 담담하게 적고 GitHub 저장소로 끝납니다.
- **형식:** 줄 번호가 있는 코드 블록, 메트릭 표, 그래프 이미지가 있습니다.
- **문체:** 반말 평서체이고 1인칭이 드러납니다. 데모를 만들 때 LLM을 썼다고 밝힙니다. 중간 길이입니다.
- **기법:** ① 설정한 값과 실제 적용된 값을 나란히 대조합니다. 선언한 설정 다음에 런타임이 실제로 받은 설정 덤프를 보여 주고, 숨은 기본값을 해설합니다. ② 계산으로 결과를 예측해 둡니다. 503이 40%여도 재시도 2회면 최종 오류는 약 6%라는 식으로, 확률로 기대값을 먼저 설명하고 관측값과 맞춰 봅니다.

### 8. Istio External Authorization의 로컬리티 로드 밸런싱 확인하기 — H / INF (가설 유지)
- **도입:** 가상 상황을 독자와 함께 가정하고("~상황을 가정해 보자"), 개념을 정리한 뒤 "적용되는지 궁금했다"는 질문으로 좁힙니다.
- **구조:** 개념(ExtAuthz, Locality LB, 조건 distribute와 outlierDetection) → 데모(kind 설정, Istio, 앱) → 로컬리티를 끈 상태와 켠 상태 비교 → 추가 자료(trafficDistribution) → 저장소.
- **근거:** 노드 이미지를 다이제스트까지 고정했고 존 레이블도 명시합니다. 요청 10회 단위로 대시보드에서 존 간 비율을 봅니다. EndpointSlice와 Envoy priority 값을 확인해 메커니즘 수준에서 검증합니다.
- **불확실성:** Ingress가 한 존에만 있다는 점, outlier 설정이 함께 바뀌어 변수를 분리하지 못한 점, 테스트하지 않은 방식이 있다는 점을 밝힙니다. 처음 예상(우회될 것)이 틀렸다고 적습니다.
- **마무리:** 관련 기능을 추가 소개하고 저장소 링크로 끝납니다.
- **형식:** 긴 YAML 블록, 흐름을 설명하는 번호 목록, 조건 다이어그램, 대시보드 스크린샷이 있습니다.
- **문체:** 반말이고 1인칭입니다. 길이는 긴 편입니다.
- **기법:** 켜기 전과 켠 후를 대조군으로 둡니다. 같은 요청 세트를 설정 하나만 바꿔 반복하고, 결과 화면 다음에 내부 상태(priority)로 원인을 뒷받침합니다.

### 21. 실행하지 않는 JavaScript를 10MiB까지 늘려봤다 (yceffort) — H / FE (가설 유지). **표본 중 근거가 가장 엄밀한 글**
- **도입:** **가장 놀라운 수치로 시작합니다**(같은 10MiB인데 준비 시간이 5배 차이). 이어 통념(트리 셰이킹 조언)에 섞인 두 가지 이득을 분리하겠다는 질문을 세우고, 결론 세 가지를 미리 요약합니다.
- **구조:** 결과 리드 → 실험 설계(세 가지 코드 형태, 생성 함수, 계측 절차) → 환경(Codespaces, CPU와 네트워크 제한) → 결과(바이트 비용 대 코드 비용 → 기울기 분해 → 트레이스로 본 원인 → 힙 → 메인 스레드 → 입력 지연 → 느린 회선 → 캐시 → 실제 라이브러리) → 결론 → **재지 않은 것** → 실험 코드와 원본 데이터.

- **기법:** ① 속도와 품질을 함께 잽니다. 가속 기법이면 반드시 평가셋 점수 변화와 짝지어 보고합니다. ② "시행착오" 섹션을 두어 측정 함정을 독자가 피할 수 있는 규칙으로 바꿉니다.

## 2. 유형 종합

### 2.1 공통 뼈대 (H 유형으로 확정된 글 16편 기준)
1. **계기와 질문:** 체감, 업무 사건, 통념 중 하나에서 출발해 "~인가?" 형태의 검증 질문으로 좁힙니다. (3, 7, 8, 21, 33, 104, 111, 116)
2. **(선택) 결과 미리 보기:** 핵심 수치나 결론을 맨 앞에 둡니다. (1, 21, 22, 100)
3. **개념과 배경 최소한:** 실험을 이해하는 데 필요한 설정과 메커니즘만 설명합니다. (7, 8, 33, 47)
4. **환경과 설계:** 버전표나 셋업, 변인과 대조군, 측정 절차를 둡니다. (1, 21, 22, 100, 111)
5. **실험·결과 반복 블록:** *조건 → 코드나 명령 → 원시 출력 → 표 → 해석* 단위가 여러 번 반복됩니다.
6. **원인 분석:** 프로파일러, 트레이스, 내부 상태 덤프로 "왜"를 설명합니다. (7, 8, 21, 33, 111)
7. **한계와 하지 않은 것** (8, 21, 22, 100, 104, 111)
8. **정리:** 요약표나 권장 사항, 다음 단계를 둡니다. 끝에 저장소와 참고 자료를 붙입니다.

### 2.2 변형 패턴
- **사례 묶음형(3):** 대상(저장소 등)마다 미니 실험을 섹션으로 반복하고 정리표로 합칩니다.
- **구현·검증·사용 3단형(28, 47):** 라이브러리나 패턴을 구현하고, 테스트와 측정으로 검증한 뒤 사용법을 안내합니다. G(가이드)와 섞인 형태입니다.
- **포팅·구현 서사형(22, 54):** 시간 순서(커밋, PR)로 결정과 문제를 서술합니다. 근거는 대조 결과와 업스트림 기여입니다.
- **반전형(33, 104, 117, 3):** "평범해 보이지만", "정석이지만" 같은 기대를 세운 뒤 측정으로 뒤집습니다.
- **주장 제목형(21, 116):** 섹션 제목 자체가 발견을 담은 문장이라, 목차만 읽어도 결론을 알 수 있습니다.
- **데모 랩형(7, 8):** kind 같은 로컬 클러스터를 만들고 → 설치 → 앱을 배포한 뒤 → 대시보드로 관찰하며, 터미널 출력이 증거가 됩니다.

### 2.3 분야별 근거 관습의 차이
| 분야 | 주로 명시하는 것 | 자주 빠지는 것 | 대표 샘플 |
| --- | --- | --- | --- |

- 경향: AI 글은 **품질과 속도를 짝지어** 보고할 때 신뢰가 높았습니다(100). 반면 **버전과 재현 정보가 가장 자주 빠지는** 분야이기도 했습니다(102, 103, 105).

- INF 글은 **원시 출력을 그대로 붙여** 증명하는 관습이 강합니다.

### 2.4 신뢰를 높이는 기법
1. 버전과 환경을 **본문 앞의 표나 고지 블록 하나로 모읍니다**. (1, 22, 21)
2. **대조군이나 기준선**을 둡니다. 로깅 OFF, AR 기준선, 주석 대조군, 설정을 끈 상태처럼 효과를 분리할 수 있는 장치입니다. (8, 21, 100, 111)
3. 반복, 워밍업, 순서 섞기, 중앙값과 IQR을 명시하고, **계측 오버헤드가 큰 실행은 본 통계와 분리**합니다. (1, 21, 47)
4. **측정 전에 메커니즘이 실제로 일어났는지** 검증합니다. 배치 로그, 커버리지 0회, 적용된 설정 덤프 같은 것들입니다. (7, 21, 47)
5. **예상과 다른 결과와 자기 오류를 정정**하는 과정을 서술합니다. (3, 21, 22, 100)
6. **"재지 않은 것", "한계점"** 섹션을 두거나 **하지 않은 주장**을 명시합니다. (21, 104, 111, 8)
7. 원시 출력(터미널, 로그)과 해석을 분리하고, 원본 데이터와 재현 명령, 저장소를 공개합니다. (1, 7, 21, 100)
8. 측정 환경이 결과에 어떻게 영향을 줄지 **방향을 예측**합니다(loopback이면 실제 차이는 더 클 것). (47)
9. 결과를 **운영 지표로 환산**하거나 **이식할 수 있는 판단 규칙**으로 바꿉니다. (33, 105)

### 2.5 신뢰를 떨어뜨리는 안티패턴
- **버전 없는 벤치마크:** 프레임워크나 라이브러리 버전이 빠져 있습니다. (102, 103, 105, 59)
- **측정값과 문서 인용값이 섞임:** 어떤 숫자를 직접 쟀는지 구분되지 않습니다. (102)
- **조건 없는 배율:** 측정 조건을 다른 곳으로 미루고 "약 1.6배"만 남깁니다. (105)
- **이상치를 보고만 하고 분석하지 않음:** OOM이나 32초 같은 값을 설명 없이 둡니다. (102)
- **제목은 "최적화"인데 측정이 없음:** (103)
- **단발 측정인데 오차를 언급하지 않음:** "오차범위 내"라고 하면서 범위 수치를 주지 않습니다. (111)
- **예시 출력처럼 보이는 결과:** 어떤 환경에서 나온 수치인지 알 수 없습니다. (6)

### 2.6 스킬 체크리스트 후보
1. **환경 블록:** OS와 커널, 런타임 빌드 번호, 핵심 라이브러리 버전, 하드웨어(GPU, vCPU), 측정 날짜를 본문 앞의 표 하나에 모았는가? AI 글이라면 모델 revision과 서빙 프레임워크 버전까지 적었는가? (1, 3, 21, 22, 100 / 부재 사례 102, 105)
2. **질문과 가설:** 도입에서 검증할 질문을 한 문장으로 세우고, 가능하면 예상(가설)도 적었는가? 결과가 예상과 같았는지 다시 언급하는가? (8, 21, 116, 33)
3. **대조군과 기준선:** 바꾼 변수 하나 외에는 같은 비교 대상이 있는가? 효과를 분리할 수 없는 경우(변수 두 개를 동시에 바꿈) 그렇다고 밝혔는가? (8, 21, 100, 111)
4. **측정 프로토콜:** 반복 횟수, 워밍업 제외 여부, 순서 섞기, 대표값(중앙값이나 평균)과 분산(IQR, 구간)을 적었는가? (1, 21, 47 / 부재 사례 102, 111, 117)
5. **메커니즘 선확인:** 측정하려는 현상이 실제로 일어났는지(로그, 커버리지, 설정 덤프) 먼저 보였는가? (7, 21, 47)
6. **원시 증거와 해석의 분리:** 코드 → 실행 출력 → 해석 순서를 지키고, 출력은 별도 블록으로 두었는가? 측정값과 인용값을 구분했는가? (1, 7, 3 / 부재 사례 102)
7. **예상 밖 결과 처리:** 반직관적인 결과나 자기 측정 오류를 숨기지 않고, 원인 분석이나 추가 실험으로 다뤘는가? (3, 21, 22, 100)
8. **한계와 일반화 범위:** "재지 않은 것"이나 "한계" 절, 또는 환경의 약점 고지가 있는가? 관측 범위 밖으로 일반화하지 않는가? (21, 104, 111, 8, 47)
9. **재현 자원:** 예제 저장소, 원본 데이터, 재현 명령을 링크했는가? (1, 7, 8, 21, 100, 111)
10. **실천할 수 있는 마무리:** 요약표, 우선순위를 둔 권장 사항, 다른 환경에 가져갈 판단 규칙 중 하나로 끝나는가? (3, 21, 100, 105)
- (보조) AI 도구를 써서 작성하거나 실험했다면 그 사실과, 판단의 주체가 사람인지 에이전트인지를 밝혔는가? (3, 7, 21, 22)
