### R-12 [Book] Istio in Action (outsider, 2021)
- **확정:** R(책 리뷰)와 E(스터디 후기)가 섞인 글 / INF. 가설 유지.
- **도입:** 표지 정보 표(별점, 저자, 출판사)로 시작해 "스터디 교재로 고른 책"이라는 선택 맥락과 MEAP(출간 전 판) 상태를 먼저 밝힌다.
- **구조:** 책 상태 → 번역 방식(구글 번역 품질) → 책 평가(부별 장점) → 추천 → `## 그룹 스터디`(기간, 방식, 다룬 부가 주제 목록) → 한 줄 소감.
- **근거·출처:** 원문 범위(14장+부록, 16버전)는 구체적이다. 평가는 전부 주관이고, "다른 Istio 책은 본 적 없다"고 비교 범위를 스스로 한정한다. 원서가 미완성이라 생긴 한계(깨진 링크, XX 표기)도 짚는다.
- **마무리:** 한 줄 소감("좋은 스터디와 책이었다").
- **형식:** 메타 정보 표 1개, 목록 1개. 이미지 없음.
- **문체:** 반말 평서체, 1인칭 '나', 약 2.5k자.
- **기법:** *리뷰 대상의 상태(버전, 완성도)와 평가자의 비교 범위를 먼저 공개한다.*

### R-18 Stack Overflow 2026 개발자 설문 (daleseo, 2026)
- **확정:** R(외부 설문 보고서 해설) / AI와 커리어 걸침. 가설 유지.
- **도입:** 독자가 아는 State of JS에 빗대 설문을 소개하고, 표본 규모(기간, 169개국, 30,903명)를 밝힌 뒤 "흥미롭게 본 부분을 골라 해석을 덧붙인다"고 선별 기준과 의도를 밝힌다.
- **구조:** 일 만족도 → 1인 개발자 증가 → AI 기본값/신뢰 → 코딩 에이전트 순위 → LLM 벤더 → 언어·도구 → 커뮤니티 성적표 → 맥락 → 마치며.
- **근거·출처:** 수치마다 해당 설문 문항이 붙어 있다. 원문의 해석("Stack Overflow는 두 가지 해석을 내놓았다")과 필자 해석("저는 ~로 읽는 편이 정확하다고 봅니다")을 문장 수준에서 나눈다. **원문의 한계를 짚는다:** 신뢰도가 31%에서 87%로 뛴 것은 문항 보기가 바뀐 탓일 수 있다는 지적, 응답자가 적은 언어(Elm, Odin)의 만족도는 과대 대표라는 지적. 원본 데이터 라이선스(ODbL)까지 안내한다.
- **마무리:** 핵심 요약 문단 → 설문 제목을 되돌려 묻는 질문 → 원문 사이트와 원본 데이터 탐색 권유.
- **형식:** 인포그래픽 이미지(본문의 "이 차트에서 파란색은…"으로 확인)를 섹션마다 넣고 바로 아래에서 읽는 법을 풀어 준다. 인용 블록 없이 짧은 직접 인용을 쓴다.
- **문체:** 존댓말(~습니다/~는데요), 1인칭 '제가', 이모지 소량, 약 9k자.
- **기법:** *원문 수치를 옮길 때 문항이나 집계 방식이 바뀌지 않았는지 확인하고, 바뀌었다면 필자의 재해석을 따로 표시한다.* *섹션 제목을 '발견 한 문장'으로 쓴다(예: "1인 개발자가 두 배로 늘었다").*

### R-25 Rails가 왜 좋았는지는… (yceffort, 2026)
- **확정:** R(키노트 리뷰)와 E(개인 에세이)의 혼합 / BE·CAR. 프레임은 R이지만 도입과 결말은 E다. **혼합형**으로 표시.
- **도입:** 10년 전 카카오에서 이유도 모르고 Rails를 썼던 개인 경험으로 시작해 키노트를 그 기억을 다시 보게 한 계기로 놓는다(동기를 서사로 공개).
- **구조:** 개인 경험 → 행사 역사(RailsConf에서 Rails World로) → 인물 배경(철학 논쟁 / 정치 논란) → 키노트 내용(사실 기술) → `듣고 나서 남은 생각`(맞는 말 / 부적절한 점 / 잣대의 비대칭 / 판단 위임 / 손코딩의 가치) → 개인 결론 → `## 참고`(12개 출처).
- **근거·출처:** 참고 목록이 아주 충실하다(영상, 세션 페이지, HN, PR 번호까지). 섹션 단위로 사실("그날 무대에서 나온 말")과 의견("남은 생각")을 분리하고 그 경계를 문장으로 선언한다("여기서 그 판단까지 하려는 건 아니다"). 논란마다 비판 측과 옹호 측 출처를 함께 단다. 화자의 주장(17배 속도 향상)을 PR 원자료로 다시 검증하고 검증 도구의 순환성까지 짚는다.
- **마무리:** 아쉬움과 심란함이라는 개인 감정, 그리고 배움에 관한 열린 성찰. 요약은 없다.
- **형식:** 비교 표(비관론과 낙관론에 댄 잣대), 인용 블록 1개(Rails Doctrine), 이미지 없음.
- **문체:** 반말 평서체, 1인칭 '나', 약 16.6k자.
- **기법:** *비판하기 전에 '맞는 말도 있었다' 섹션을 먼저 둔다(스틸맨).* *발표자의 주장을 1차 자료(PR, 커밋)로 교차 검증한다.* *사실 서술 구역과 의견 구역을 헤딩으로 나눈다.*

### R-43 클로드는 왜 날씨를 계산하지 못할까 (evan-moon, 2026)
- **확정:** **C(개념 해설)로 재분류 제안** / AI·과학계산. 특정 논문 리뷰가 아니라 트랜스포머, 푸리에 변환, FNO, PINO를 차례로 설명하는 글이다.
- **도입:** "LLM 만능론"이라는 통념 → 함정 제시 → 데이터가 부족한 물리 문제 → "이번 포스팅에서는 ~를 따라가 보려고 한다"고 로드맵을 공개.
- **구조:** 트랜스포머가 잘하는 것과 못하는 것 → PINO가 푸는 문제 → 푸리에 변환 → 재료 조립(FNO → PINO) → 현실 속 Neural Operator(응용 / "그래서 만능일까") → 마치며.
- **근거·출처:** Pangu-Weather(Nature 2023), ECMWF AIFS 운영 시점 같은 사실에 출처 기관과 연도를 단다. **한계를 별도 섹션으로 둔다(3가지).** 과장된 소개 글을 바로잡는다("반드시 지키는" 모델이 아니라 "대체로 잘 지키는" 모델).
- **마무리:** 탐구 동기 회고 → 한 문장 교훈("본 적이 있을까?"로 질문 바꾸기) → 개발자의 LLM 사용으로 확장.
- **형식:** TypeScript 코드 12블록, 수식, 개발자 비유(React 프레임워크, 블러 필터, 게임 update 루프). 표와 인용 블록 없음.
- **문체:** 반말 평서체, 1인칭 '필자', 35k자 이상(장문).
- **기법:** *낯선 수식은 독자 도메인의 코드로 옮겨 "꼴랑 이 정도"임을 보여 준다.* *소개 대상 기술에 '그래서 만능일까' 섹션을 반드시 붙인다.*

### R-58 Jev 간단 분석 (bcho, 2026)
- **확정:** R(신제품 첫인상 분석) / AI. 유지하지만 **품질이 낮은 R 샘플**.
- **도입:** "운이 좋아 접근권을 얻었다"고 경위를 밝히고 첫인상(분류 모델에 가깝다)부터 말한다.
- **구조:** 첫인상과 전망 문단 → `1. 주요 활용 용도 5가지` → `2. 단순 분류 모델이 다양하게 쓰이는 이유`.
- **근거·출처:** 데모 사이트 URL 하나. **본문 후반이 AI가 만든 정리**라고 스스로 밝힌다("AI를 이용한 사례 분석 정리 내용"). 공개는 정직하지만, 수치(100~300ms, $0.001 이하)의 출처나 검증이 없다. 전망("조만간 인수되지 않을까?")은 근거 없는 추측이다.
- **마무리:** 마지막 목록 항목으로 끝남. 결론 없음.
- **문체:** 앞은 반말, 후반 AI 정리는 존댓말이라 **문체가 섞인다**. 약 2.6k자.
- **기법/안티패턴:** *AI가 만든 부분을 공개한 것은 좋다.* 그러나 *AI 요약을 검증 없이 본문에 붙이고 수치 출처를 빠뜨린 것은 안티패턴*이다.

### R-60 AI 코딩의 발전단계 (bcho, 2026)
- **확정:** R(외부 글 해설 + 사례) / AI. 유지.
- **도입:** 리서치하다 찾은 글이라는 계기 → 원문 링크(martinfowler.com, Kief Morris) → 이해에 필요한 전제 개념(Why/How Loop)부터 정의.
- **구조:** 전제 개념 → 1단계 Outside → 2단계 In → 3단계 On(하네스) → 다음 단계 Agent Flywheel(랄프 루프, 실패 사례) → 현재 위치 진단.
- **근거·출처:** 원문 링크는 맨 앞에 있다. 다만 4단계(Flywheel)와 Amazon 사고 사례는 필자가 덧붙인 것인데, 원문과 덧붙인 부분의 경계가 흐리다. "가트너 리포트 11%"는 보고서명이나 연도가 없다. Amazon 사고 3건에는 날짜와 규모가 있지만 출처 링크가 없다.
- **마무리:** 현재 위치(3단계가 주류) 진단과 방향 전망. "다른 글에서 자세히" 예고.
- **형식:** 비교 목록(In loop 대 On loop). 표와 이미지 없음. 약 3.4k자, 반말.
- **기법:** *개념 차이를 '마음에 안 드는 결과가 나왔을 때 각각 무엇을 고치는가'라는 한 장면으로 대비한다.*

### R-63 AI 코딩이 오히려 생산성을 떨어뜨린다? – Anthropic 논문 (bcho, 2026)
- **확정:** R(논문 요약) / AI. 유지.
- **도입:** 논문 arXiv 링크 → 핵심 결과 → **바로 연구 한계(1시간 제약, 작은 표본) 명시** → 흥미로운 지점(6가지 패턴)으로 범위를 좁힘.
- **구조:** 저점수 패턴 3개 → 고점수 패턴 3개 → 결론 → 개인 소감.
- **근거·출처:** 원문 링크가 있고, 각 패턴에 n(4, 4, 4, 2, 3, 7)을 붙여 표본 크기를 드러낸다. 논문 안의 인용(Lee et al.)도 남겼다. 그러나 결론부 "궁극적으로 전문 기술 저하로 이어진다"는 단정은 n=2~7 하위 그룹 결과를 넘어선 일반화다. 제목의 '생산성 저하'와 본문의 측정 지표(퀴즈 점수, 이해도)도 어긋난다(제목 과장).
- **마무리:** 필자 자신의 걱정과 사용 방식(70~80% 품질, 하이브리드) → 논문은 "경고"라는 느낌.
- **문체:** 반말, 약 2.4k자.
- **기법:** *요약 첫머리에 연구 한계를 먼저 밝힌다.* *하위 그룹마다 n을 단다.* 안티패턴: *제목과 결론이 본문 근거보다 강하다.*

### R-69 (요약) Agentic Misalignment (johngrib, 2026)
- **확정:** R(논문 발췌 스크랩) / AI. 유지.
- **도입:** 제목에 '(요약)'을 달고, 목차 → `## 원문`(글, PDF, 코드 저장소 링크 3개) → `## 개요` 순서.
- **구조:** 원문 링크 → 개요 → `PDF N쪽: 핵심 주장` 형식 헤딩 5개.
- **근거·출처:** **가장 엄격한 출처 처리.** 헤딩에 PDF 쪽수를 달고, 원문 영어를 인용 블록으로 둔 뒤 그 아래 번역이나 요약 목록을 붙이고, 필자 감상은 짧은 목록 항목으로 분리한다("좀 무섭다"). 실험의 작위성도 짚는다("매우 작위적인 케이스", "시뮬레이션이므로 실제 피해 없음" 주의).

## 3. 유형 종합 — R(리서치·리뷰)

### 3.1 공통 뼈대 (실질 R 9편 기준: 12, 18, 25, 60, 63, 69, 96, 99 + 43)
1. **원문 식별:** 무엇을(제목, 저자, 학회·기관, 연도, 링크) 읽었는지 맨 앞에 둔다(18, 60, 63, 69, 96, 99).
2. **동기와 범위:** 왜 읽었는지, 어디를 골라 다룰지(18 "흥미롭게 본 부분", 63 "6가지 패턴", 99 "생각할 거리").
3. **(선택) 신뢰도 고지:** 원문의 한계와 재현 가능성(63, 99), 비교 범위(12).
4. **배경 개념:** 원문을 이해하는 데 필요한 최소 개념(60 Why/How Loop, 99 RL 비용, 96 MT/LM/MLM).
5. **본문:** 원문 구조를 따르거나(69, 96, 60) 필자가 고른 발견을 따른다(18, 63).
6. **필자 해석 / 한계:** 별도 섹션이나 문장 표지로 분리한다.
7. **마무리:** 요약 + 일반화한 교훈 + (원문 탐색 권유, 다음 편 예고, 개인 소회).

### 3.2 변형 패턴
- **스크랩형(69, 96):** 헤딩 = 원문 위치(PDF 쪽수) 또는 결론 명제. 결론 섹션이 없다. 원문 인용 비중이 높다.
- **보고서 해설형(18):** 발견 한 문장을 헤딩으로 쓰고 수치를 해석한다. 독자에게 질문하며 끝낸다.
- **리뷰+에세이형(25):** 개인 서사로 열고 닫는다. 가운데는 사실과 의견을 헤딩으로 나눈다. 참고 목록이 길다.
- **실무자 비평형(99):** 원문 요약 뒤에 '내 가설'을 붙인다. 원문의 결함을 지적한다.
- **짧은 소식형(58, 60, 63):** 2~3k자, 원문 링크 1개, 결론에 개인 걱정이나 전망.
- **R로 위장한 비R(52, 53):** 출간 안내와 카탈로그. 근거 구조가 없다.

### 3.3 분야별 차이 — 특히 AI 리서치 글의 출처 처리
- **AI 논문을 다루는 글(63, 69, 96, 99)은 원문 링크가 사실상 필수**이고 실제로 모두 링크가 있다. 차이는 *해석을 분리하는 정밀도*에서 난다.
  - 정밀: 96(술어로 저자와 필자 구분), 69(인용 블록, 번역, 감상 3층), 99("내 생각에는" + ablation 부재 지적).
  - 느슨: 63(요약은 정확하지만 결론부에서 하위 그룹 n=2~7 결과를 "전문 기술 저하로 이어진다"로 일반화. 제목의 '생산성'과 본문 지표 불일치), 60(원문과 덧붙인 사례의 경계가 흐림, "가트너 11%"에 출처 없음), 58(AI 생성 정리를 검증 없이 게시).
- **AI 산업 동향 글(18, 44, 60)은 수치가 많다.** 18과 44는 수치마다 기관과 연도를 달고 측정 방식의 변화까지 짚는다. 60은 사고 사례의 날짜와 규모는 있지만 링크가 없다.
- **비AI 리뷰(12 책, 25 발표):** 원문이 하나의 덩어리라서 '버전과 상태'(12), '1차 자료 교차 검증'(25)이 신뢰를 만든다.
- **AI 분야의 고유 위험:** 빠른 소식 전달 욕구 때문에 *제목이 결과보다 강해지고*(63), *AI가 쓴 요약이 섞인다*(58). 반대로 상위 필자들은 *원문 스스로 밝힌 약점*(44의 METR "약한 근거", 18의 문항 변경)을 그대로 옮기는 방식으로 신뢰를 얻는다.

### 3.4 신뢰를 높이는 기법
- 원문 메타 정보와 링크를 첫 화면에 둔다(63, 69, 96).
- 연구 한계를 요약 **앞**에 밝힌다(63, 99).
- 하위 그룹과 표본 크기를 숫자로 붙인다(63 n=4…, 18 30,903명).
- 저자 주장과 필자 해석을 문장 술어나 헤딩으로 나눈다(96, 25, 18).
- 원문 수치의 측정 방식이 바뀌었는지 점검한다(18).
- 주장을 1차 자료로 교차 검증한다(25 PR과 커밋).
- 비판하기 전에 동의 지점을 밝힌다(25).
- 소개하는 기술의 한계를 별도 섹션으로 둔다(43).
- 원문 위치(쪽수)를 헤딩에 넣는다(69).
- 이미지 출처를 일괄 고지한다(96).

### 3.5 안티패턴
- 제목이 본문 근거보다 강하다(63).
- 출처 없는 산업 수치를 쓴다(60 가트너, 58 지연과 비용 수치).
- AI 생성 요약을 검증 없이 붙이고 문체가 섞인다(58).
- 원문 내용과 필자가 덧붙인 사례의 경계가 흐리다(60).
- 이해관계를 밝히지 않은 추천(52, 53. 본인 책).
- 결론 없이 끝나는 스크랩을 '요약'이라 부른다(69. 노트로는 괜찮지만 블로그 글로는 마무리가 약하다).
- 원문 인용 비중이 과도하다(69. 인용 블록 11개).

### 3.6 R 스킬 체크리스트 후보
1. 첫 문단 안에 원문의 제목, 저자·기관, 연도, 링크를 밝혔는가? *(63, 69, 96, 99, 60)*
2. 왜 읽었고 어느 범위를 다루는지(선별 기준) 썼는가? *(18, 63, 99)*
3. 원문의 한계(표본, 시간 제약, 재현 가능성, 빠진 실험)를 요약보다 먼저 혹은 별도 섹션으로 밝혔는가? *(63, 99, 43)*
4. 원문 주장과 내 해석을 문장 표지("저자들은 ~라고 한다" 대 "내 생각에는")나 헤딩으로 구분했는가? *(96, 25, 18, 44)*
5. 옮긴 수치마다 출처와 측정 조건(문항, 표본, 기준)을 붙였고, 집계 방식이 바뀐 비교는 아닌지 확인했는가? *(18, 63, 44 / 반례 60, 58)*
6. 제목과 결론이 본문 근거의 강도를 넘지 않는가(하위 그룹 결과를 전체로 일반화하지 않았는가)? *(반례 63)*
7. 비판하기 전에 동의할 만한 지점을 먼저 정리했는가? *(25, 56)*
8. AI 도구로 만든 요약이나 번역을 썼다면 그 사실을 밝히고 수치와 사실을 원문으로 대조했는가? *(58 반면교사)*

## 4. 유형 종합 — E(회고·에세이)

### 4.1 공통 뼈대
1. **계기 또는 사실 앵커:** 기간, 숫자, 사건으로 시작한다(11 "7회", 30 "1,000만", 50 "배포 완료", 75 "1년").
2. **쓰는 이유와 독자 범위:** 왜 기록하는지와 누구에게 해당하는지(29, 31, 92, 93).
3. **맥락 공개:** 필자의 위치(직책, 팀 규모, 조직 조건)(11 팀 리드, 75 혼자에서 7명 팀으로, 55 공적 자금, 31 CTO).
4. **본문:** 시간순(30, 31, 79, 93), 주제별(75, 50), 질문별(92, 70) 가운데 하나.
5. **어려움과 실패:** 대부분 한 군데 이상 있다(11, 20, 30, 31, 50, 75, 79).
6. **교훈이나 원칙으로 압축.**
7. **다음 계획이나 열린 질문으로 마무리**(11, 20, 30, 50, 57, 78, 92).

### 4.2 변형 패턴
- **연대기형(30, 31, 79, 93):** 연·월 헤딩. 사건마다 '왜 그랬나'를 붙인다. 아주 길어지기 쉽다(31, 79는 25k자 이상).
- **프로젝트 사후 정리형(20, 50):** 단계와 실험 → 수치 → 실패 → 다음 단계. H 유형과 경계가 흐리다.
- **논증형 에세이(44, 55, 56):** 외부 글이나 연구를 출발점으로 삼아 이론 틀(제약 이론, 마르크스, 유물사관)로 논증한다. R과 경계가 흐리다.
- **소신과 권고형(29, 78):** 짧다. 비유와 일화. 독자에게 직접 권고한다.
- **Q&A형(92, 70, 93 FAQ):** 독자의 질문을 그대로 헤딩으로 쓴다. 개조식.
- **활동 보고형(57, 11):** 활동 목록과 감사. 수치와 실패가 적다.

### 4.3 분야별 차이
- **AI와 조직 주제(44, 50, 92, 55, 56):** 2026년 글들은 거의 모두 AI 도입 경험을 다룬다. 신뢰도 차이는 *측정했느냐*에서 갈린다. 44는 외부 연구로, 50은 자체 벤치마크(PR 180건)로 받친다. 92는 경험 기반 조언이지만 "정답은 없다"고 범위를 제한한다. 50의 "83% 절감"처럼 자기 보고 수치가 측정 방식 없이 쓰이는 것이 이 분야의 흔한 약점이다.
- **커리어(29, 30, 93, 92):** 상담에서 받은 질문이 집필 계기다. 범위 제한 문구("모두에게 해당하지 않는다", "답은 아니다")를 쓰는 비율이 높다.
- **기술 학습 회고(11, 75, 20):** 구체적인 기술 사례(React Query와 SWR 비교 PR, 측정 조건)가 들어갈수록 H나 T에 가까워진다.
- **해외 독자를 겨냥한 다국어 블로그(55~57):** 외부 영어권 글을 인용 블록으로 끌어와 대화하듯 쓴다. 각주와 페디버스 안내가 붙는다.

### 4.4 신뢰를 높이는 기법
- 첫 화면에 성과와 미확인 사항을 함께 둔다(20).
- 수치에 조건(기준, 환경, 횟수)을 붙이고, 측정값, 환산값, 운영값을 나눈다(20).
- 실험 설계(표본, 기준, 일치도 정의)를 공개한다(50).
- 원래 원칙과 이번에 어긴 이유, 그리고 감수한 비용(31).
- 자기 경험을 대조군으로 쓰되 일반 해법이 아니라고 명시한다(55).
- 적용 대상을 글 앞에 밝힌다(29, 92, 93).
- 경험하지 않은 것에는 판단을 유보한다(93).
- 과거의 회의적 입장과 무엇이 그것을 바꿨는지(11).
- 실패와 감정(상처, 미안함)을 숨기지 않는다(75, 78, 31).
- 연구 결론과 내 해석을 분리한다(44).

### 4.5 안티패턴
- 측정 방식 없는 자기 보고 성과 수치("평균 83% 절감", "절반도 안 되는 리소스")(50).
- 교훈을 단정형으로 일반화하는데 사례가 하나뿐이거나 없다(29는 범위 제한으로 일부 상쇄).
- 활동 나열만 하고 실패나 판단이 빠진 회고(57).
- 지나치게 긴 연대기(31, 79): 독자가 핵심 결정을 찾기 어렵다. 요약이나 목차가 없으면 더 심하다.
- 글 끝의 홍보가 마무리 효과를 희석한다(92, 93의 강의와 채널 홍보).

### 4.6 E 스킬 체크리스트 후보
1. 첫 문단에 기간, 규모, 수치 같은 사실 앵커와 이 글을 쓰는 이유를 밝혔는가? *(11, 30, 31, 50, 75)*
2. 필자의 맥락(역할, 팀 규모, 조직 조건)을 밝혀 독자가 일반화 범위를 판단할 수 있게 했는가? *(11, 31, 55, 75, 20)*
3. 주장의 적용 대상과 한계를 명시했는가("모두에게 해당하지 않는다", "정답은 아니다")? *(29, 92, 93, 55)*
4. 핵심 주장마다 구체적 사례 한 건이나 측정값 하나로 받쳤는가? 수치에는 기준과 조건, 측정 방법이 있는가? *(20, 50, 44 / 반례 50의 83%)*
5. 실패, 미완료, 아쉬움을 최소 한 곳 이상 기록했는가? *(20, 11, 31, 50, 75)*
6. 결정을 기록할 때 '평소 원칙 → 이번 선택과 조건 → 치른 비용'을 썼는가? *(31, 20)*
7. 외부 연구나 남의 글을 끌어왔다면 그 결론과 내 해석을 문장으로 분리했는가? *(44, 55, 56)*
8. 마무리가 교훈 한 문장 + 다음 계획이나 독자에게 던지는 질문으로 끝나는가(홍보가 마무리를 덮지 않는가)? *(20, 30, 44, 50, 92)*
