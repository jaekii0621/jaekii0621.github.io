- **불확실성:** `DNS_ROUND_ROBIN`이 이름과 달리 첫 주소만 쓴다는 오해를 바로잡는다.
- **마무리:** 예시로 끝나며 요약이 없다.
- **형식:** YAML 4블록, 중첩 목록
- **문체:** 평서체(~다), 1인칭 없음, 약 4.7천 자
- **기법:** (1) 필드를 설명할 때 "이름이 주는 오해"를 함께 교정한다. (2) 단일 리소스에서 연계 리소스를 조합하는 예시로 넓혀 간다.

### 15. 파이썬 3.15 lazy import로 프로그램 시작 시간 줄이기 (Dale Seo, 2026-10-18)
- **유형/분야:** G/BE 확정
- **도입:** 독자가 겪어 봤을 증상을 질문으로 던진다(`--version`도 굼뜨다). 이어 기존 우회법, PEP 810 도입, 글 범위를 예고한다(문법, 측정, 에러 시점, 못 쓰는 곳, 일괄 적용).
- **구조:** 왜 느린가(측정) → 기본 문법 → 시작 시간 비교 → 에러는 처음 사용할 때 → 쓸 수 없는 곳 → 부수효과 모듈 주의 → 타입 힌트 import → 기존 코드 일괄 적용 → 마치며
- **근거:** 파일명 라벨, 코드, "결과" 블록을 쌍으로 붙인다. `-X importtime`으로 측정하고, 30회 중앙값으로 50.4ms → 25.2ms를 보인다. 측정 환경은 인용 박스로 밝힌다(Apple Silicon, 3.15.0, 비율 위주로 봐 달라는 당부). PEP 문서와 3.15.0 실제 동작이 다른 지점(none 모드 미지원)을 짚고, Ruff·Mypy·Pyright 지원 버전을 적는다.
- **불확실성:** 주의 섹션이 셋이다(에러 시점, 금지 위치, 부수효과). 서드파티 코드에서는 충분히 테스트하라고 권한다.
- **마무리:** 요약 → 꼭 기억할 3가지 → 실습 시작법(uv, 구버전 uv 주의) → 공식 "새로운 기능" 문서
- **형식:** 코드 22블록, 표와 이미지 없음
- **문체:** 존댓말(~요/~습니다), 이모지, 약 8.9천 자
- **기법:** (1) 전후 수치를 측정 환경, 해석 한계와 함께 제시한다. (2) 문서와 실제 동작이 다른 지점을 직접 실행해 보고 표시한다.

- **마무리:** 요약 → 최소 첫 행동 제안(GitHub MCP 하나만) → 관련 글 3개
- **형식:** 코드 중심, 표 없음
- **문체:** 존댓말 ~요, 약 10.7천 자
- **기법:** (1) 갱신하는 글은 Updated 날짜를 표기하고 "예전에는 X, 지금은 Y"를 본문에 남긴다. (2) 마무리에서 독자가 오늘 할 일 하나를 제시한다.

### 17. 1Password MCP 서버: 클로드 코드로 .env 안전하게 관리하기 (Dale Seo, 2026-10-07)
- **유형/분야:** G/AI 확정. 벤더 주장을 검증하는 성격을 겸한다.
- **도입:** 기능을 발견한 계기와 걱정(에이전트가 키를 꺼내 가면?)으로 연다. 글의 목표와 함께 벤더 문구가 어디까지 사실인지 확인하겠다는 검증 목표를 밝힌다. 기준 버전을 한 줄로 명시한다(1Password for Mac 8.12.40, 클로드 코드 2.1, 플러그인 0.1.0).
- **구조:** 무엇을 하나(도구 표) → 앱에서 켜기 → 플러그인 설치 → 순서를 어기면 15분을 기다려야 한다 → .env 옮기기 → 승인 창 2단계 → 마운트된 .env는 named pipe → 에이전트는 정말 값을 못 볼까 → 서비스 계정과의 차이 → 마치며
- **근거:** 기준 버전을 명시하고, 릴리스 노트로 기능 변천사를 정리하며 공식 문서 일부가 낡았다고 경고한다. 베타이며 Mac·Linux만 지원한다는 점, 실패 출력 원문(`✘ Failed to connect`)도 담았다.
- **불확실성:** "도구가 값을 돌려주지 않는다"와 "에이전트가 값을 볼 수 없다"가 다르다는 것을 실험으로 보인다.
- **마무리:** 확인한 사실 요약 → 남는 위험 → 권고(권한 규칙과 샌드박스)
- **형식:** 도구 표, 코드 17블록
- **문체:** 존댓말, 1인칭("저는 순서를 거꾸로 했습니다"), 약 11천 자
- **기법:** (1) 실패한 순서를 감추지 않고 헤딩으로 끌어올려 원인과 회복법을 보인다. (2) 벤더 문구를 가설로 두고 직접 검증한다.

- **문체:** 평서체, 비유가 많다(도로 사고), 매우 길다(12천 자 이상).
- **기법:** (1) 서두에 글의 지도와 순서의 근거를 둔다. (2) 증상 조합에서 확인할 곳으로 가는 판단표를 쓴다.

- **기법:** (1) 소제목을 독자가 실제로 마주치는 순서대로 질문형으로 배열한다. (2) 대안 A와 B를 나란히 보이고 선택 조건을 제시한다.

### 2.3 분야별 근거 관습
- **AI:** 버전이 가장 빨리 낡는 분야라 시점 표기가 가장 중요한데도 관습이 갈린다. 좋은 쪽은 버전 경계(101: 0.137+/0.142+), 기준 버전 한 줄(17), "N년 N월 기준"과 Changelog(91), 갱신일(16)을 쓴다. 나쁜 쪽은 출처 없는 수치 표(62), 버전 없는 설치 명령(X1, 61)이다. 출력은 스크린샷으로 대신하는 경우가 많다(90, 91, 49). AI가 작성했다는 고지가 나타나기 시작했다(61 본문 고지, 101 `ai_assisted` 라벨). 다만 무엇을 사람이 검증했는지까지 적은 글은 없다.
- **BE:** 언어·프레임워크 버전으로 기능의 경계를 긋는다(15 Python 3.15.0, 36 Spring Boot 2.3/2.4, 48 Batch 4.1). 측정값을 근거로 쓴다(15 중앙값, 36 레이어 MB). 코드와 결과 블록 쌍이 표준이다.
- **INF:** 환경 명세와 실행 출력이 가장 엄격하다(121은 전 구성요소 버전, 51은 이미지 태그 고정). 검증 명령과 정상 상태 출력(`get pods`, `Running`)이 관습이다. 하지만 9, 124처럼 설정 YAML 중심의 글은 제품 버전을 빠뜨리기 쉽다.
- **TOOL:** `$` 프롬프트와 실제 출력, 최소 재현 저장소(65)를 쓴다. 도구 종류와 버전 확인 명령(66 `ctags --version`)을 둔다. 위키형이 많아 항목별 시점 관리가 약점이다(67, 84는 2019년 글인데 시점 경고가 없다).

### 2.4 신뢰를 높이는 기법
1. **기준 환경을 서두 한 줄에 둔다.** 버전과 OS를 쓴다(17, 51, 121, 15).
2. **명령 → 실제 출력 → 판정 기준.** 출력은 텍스트로 싣는다(51, 65, 101, 121).
3. **실패를 재현해 보인다.** 에러 원문, 원인, 회복법을 함께 쓴다(17, 65, 101, 121, 48).
4. **측정값에 환경과 해석 한계를 붙인다**(15 "비율 위주로 봐 달라").
5. **문서와 실제가 다른 지점을 표시한다**(15 PEP와 3.15.0, 17 공식 문서가 Labs 메뉴라고 안내함, 66 2011년 설정 비호환).
6. **"언제 쓰지 말까"와 "대가"를 명시한다**(61, 101, 15).
7. **확인 못 한 것은 "추측"이나 "미검증"으로 표시한다**(91, X1).
8. **시점을 표기하고 이력을 남긴다**(16 Updated, 91 기준일, 66 Deprecated).
9. **실습 정리 단계를 둔다**(51 삭제 명령).

### 2.5 신뢰를 떨어뜨리는 안티패턴
- **출처 없는 수치 표(62).** 자주 바뀌는 가격과 한도를 표로 단정한다. 출처 링크, 확인 날짜, 추정 여부가 없다. 일화(13,800달러)에도 링크가 없다. → 표 바로 아래에 "출처 / 확인일 / 공식 비공개 시 추정"을 의무로 단다.
- **실행하지 않은 튜토리얼(X1).** 명령은 있는데 출력이 없고, 결과 표는 빈 양식이며, 미검증 고지는 맨 끝에 있다. → 실행하지 못했다면 (a) 고지를 서두로 올리고, (b) 섹션마다 검증 상태 표시(검증됨 / 미검증)를 달고, (c) 글의 성격을 "튜토리얼"이 아니라 "학습 계획"이나 "개요"로 바꾼다.
- **시점 없는 오래된 레시피(84, 67, 95).** 2019~2021년 명령과 수치를 시점 경고 없이 제시한다.
- **`latest` 태그와 무버전 설치(121의 vLLM 이미지, X1, 90).** 재현성이 깨진다.
- **복붙 오류(124).** 섹션 번호가 겹치고 설정 블록이 잘못 들어갔다. 신뢰를 직접 깎는다.
- **출력을 스크린샷으로만 제시(90, 91, 48).** 검색과 복사가 안 되고 접근성도 떨어진다.
- **AI 작성 고지에 검증 범위가 없다(61, 101).** 고지 자체는 좋지만 "무엇을 사람이 실행해 확인했는가"가 빠져 있다.

### 2.6 스킬 체크리스트 후보
1. **서두에 "대상 독자 / 목표 / 기준 환경(도구 버전, OS) / 작성일" 네 가지를 둔다.** 버전은 한 줄로 쓴다. (17, 51, 121, 15 / 결여 사례 62, 9, 124)
2. **모든 핵심 명령 뒤에는 저자가 실제로 얻은 출력을 텍스트로 붙이고, 성공 판정 기준을 한 문장으로 적는다.** (51, 65, 101, 121 / 반례 X1)
3. **실행하지 못한 단계는 해당 위치에 "미검증"으로 표시하고, 전체 검증 범위는 서두에 밝힌다.** (X1 끝에만 고지, 91 "추측")
4. **가격, 한도, 기본값처럼 바뀌는 수치에는 출처 링크와 확인 날짜를 붙인다. 공식 수치가 없으면 추정이라고 쓴다.** (62 반례, 16 일부, 91 기준일)
5. **"주의 / 흔한 실수 / 언제 쓰지 말아야 하나"를 별도 섹션으로 두고, 가능하면 실제 에러 원문과 회복법을 함께 적는다.** 함정이 셋 이상이면 "증상 | 원인 | 해결" 표로 만든다. (101, 17, 121, 15, 61, 65)
6. **공식 문서 링크를 넣고, 공식 문서와 실제 동작이 다르면 그 지점을 표시한다.** (15, 17, 66 / 결여 101, 62)
7. **가장 짧은 성공 경로(스모크 테스트)를 본격 설정보다 먼저 제시한다.** (101 PONG, 51 워드프레스 1차 목표)
8. **마무리는 요약, 독자의 다음 첫 행동 하나, 참고 링크 순으로 쓴다. 실습형이면 정리(cleanup) 단계도 넣는다.** (16, 15, 51, 101)
9. **갱신하는 글은 Updated 날짜와 변경 이력("예전에는 X, 지금은 Y")을 남기고, 낡은 내용은 지우는 대신 Deprecated로 격리한다.** (16, 66 / 반면교사 67)
10. **AI 도움으로 작성했다면 고지와 함께 사람이 직접 실행해 확인한 범위를 적는다.** (61, 101 라벨만 있고 범위 없음, X1 범위 고지 모범)
